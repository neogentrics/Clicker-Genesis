# Clicker Genesis — Project Context

Bible-verse idle/incremental clicker for Android (Unity, URP 3D Core template). Goal: help players learn and memorize scripture through play. Micro-transactions exist but are never required for progress or content.

**Full design doc (source of truth, keep it updated as design evolves):** https://app.notion.com/p/3aead37812e881c99578d596f3a29921

## Guiding principle
Scripture text is never altered, paraphrased, or reinterpreted. Only unedited, recognized translations are used. This constraint overrides convenience in any implementation decision.

## Confirmed design (do not re-litigate without the user explicitly reopening it)

- **Currency:** Ink. Earned by tapping and by passive/idle upgrades ("scribes").
- **Core action:** spend Ink to buy the *next* verse in canonical order within your active book (no skipping within a book in v1). Buying reveals verse text + reference.
- **Screen split (CONFIRMED 2026-07-31, reopens/supersedes the old single-screen assumption):** tapping and buying are now separate screens — a Clicker screen (tap-for-Ink only) and a Buy Verse screen (spend Ink, verse reveal), navigated between via a button. This was an explicit, deliberate user decision, not incidental UI organization — the core loop's pacing now includes a screen switch between tap and buy.
- **Chapter bulk-buy:** sum of remaining verse costs in the chapter × 0.75 (25% discount).
- **Pricing curve:** `verse_cost(n) = base_cost × growth_rate ^ n`, where `n` resets per book (each newly unlocked book starts approachable, doesn't inherit endgame pricing). `base_cost`/`growth_rate` must be data-driven (config/ScriptableObject fields), never hardcoded magic numbers — they'll be rebalanced after playtesting.
- **XP/Leveling:** small XP per verse, larger per chapter, larger still per book completed. No separate "clicker leveling" or achievement subsystem in v1 — XP comes only from actions already in the loop.
- **Book unlocking:** player picks ONE starting book for free on first run (personalization hook). Locked into that book until prestige-eligible (a level threshold, reachable mid-book — does NOT require finishing the book). Post-prestige book choice is free-pick (not strict canonical order) within the currently-unlockable pool.
- **Testament scope (v1):** Old Testament only. No Testament selector/lock built yet — that pool is just "all OT books" for now. New Testament is a deferred content update; the original hard-lock idea (pick a Testament, stuck until it's 100% done) is a seed for later, not a v1 build target.
- **XP formula (CONFIRMED placeholder constants, implemented 2026-07-31):** content-completion based, not RPG/combat based. `XpConfig` ScriptableObject: xpPerVerse=1, xpPerChapterBonus=10, xpPerBookBonus=100. Level threshold curve: XP needed to go from level L to L+1 = `levelXpBase * L` (linear growth, levelXpBase=50) — cumulative XP at start of level L = `levelXpBase * (L-1) * L / 2`. `prestigeLevelThreshold`=5 (placeholder). All values explicitly placeholder pending playtesting, same rule as the Ink pricing curve — but now real, working, data-driven code, not just a formula on paper.
- **Clicker/Manager subsystem direction:** standard idle-game shape (Cookie Clicker / AdVenture Capitalist). "Scribes" = passive Ink/sec generators bought with Ink on an escalating curve. "Managers" = one per scribe type, gated by BOTH player level AND an Ink cost (REVISED 2026-08-04 — supersedes the earlier "auto-unlocks by level alone" description; managers now require an explicit purchase once level-eligible). Exception: Adam (first manager) stays free once level-eligible, no Ink cost — same "personalization hook stays reachable early" pattern as the free starting book. Exact rates/manager levels/costs still open (numeric only).
- **Scribes/Managers tab split (CONFIRMED 2026-08-04, BUILT 2026-08-04):** ClickerScreen's Scribes panel has a second tab, "Managers," listing all managers and their unlock cost/status (Locked-by-level / buyable / Owned). `ManagerListUI.cs` + `GameLoopController.BuyManager()`. Verified functionally via script test; awaiting user's own Play confirmation. Future scope (not v1): some managers Prestige-gated for certain books; paid (real-money) manager unlocks as a convenience shortcut, but per the IAP-never-required guiding principle above, any such manager must always also be obtainable through normal Ink/Prestige play — never purchase-exclusive.
- **Pending to-do, not yet built (relayed 2026-08-06 from a parallel "Bible indexing" planning session, user's explicit correction there):** `ManagerListUI.cs` row text is too verbose — drop the flavor-text description entirely, each row should show only the manager's name + their actual active bonus/perk. Also needs to leave room for additional perk lines once a manager gains a bonus from something other than its own level/Ink unlock (a Grace Skill Tree node, or the not-yet-built submanager system below) — surface those on the row too when they apply. Pick this up next time `ManagerListUI.cs` is open.
- **Books tab on Buy Verse screen (CONFIRMED 2026-08-04, still not built — the Grace Skill Tree it depends on is now built, this UI itself isn't):** third tab alongside Verses/Chapters, reading `PrestigeSkillSystem.IsBookUnlocked(resourceId)` to show which books the player has unlocked via the Book Progression skill-tree branch. Does not appear in the tab row at all until the player has prestiged at least once — not merely grayed out, fully hidden, same progressive-disclosure pattern as the ClickerScreen "Skill Tree" button.
- **Scribe/Manager theming (CONFIRMED 2026-07-31, Genesis locked in as the template):** each unlocked book gets its own scribe tier names (objects/motifs from that book) and manager names (real named characters from that book, each tied to something they actually do in the narrative — not arbitrary name-slapping). Genesis pilot (starting set, explicitly NOT exhaustive — user noted more scribes/managers can be added from Genesis later): Reed Pen → Papyrus Scroll → Stone Tablet → Oil Lamp → Ark's Manifest → Covenant Seal → Jacob's Ladder → Joseph's Storehouse (8 scribe tiers); managers Adam (Reed Pen), Noah (Ark's Manifest), Abraham (Covenant Seal), Jacob (Jacob's Ladder), Joseph (Joseph's Storehouse). This is content/naming theming layered on the shared v1 Ink economy — does NOT require the separate per-book currencies from the v1.x/v2 phase below. Other books' rosters get authored book-by-book as those books are actually built, not all up front.
- **Art direction (confirmed 2026-07-31):** two-layer system. Base UI = warm parchment & minimal ink (calm, legible, mobile-fast — used ~95% of the time). Accent layer = stained-glass *technique* (bold jewel-tone color blocks, dark linework, glow) reserved for reward moments only (verse reveal, chapter/book complete, prestige) — explicitly NOT literal cathedral/church imagery. Starting palette + typography proposal is in the doc folder overview (see below), not finalized art.
- **Save/persistence system — REOPENED 2026-08-07, BUILT 2026-08-08.** Was deferred since 2026-07-31 ("we'll get to that saved gaming system later"), reopened by the user with a narrower, more urgent driver than the original full vision: unblock playtesting specifically — testers shouldn't lose progress relaunching the game or picking up an update. Full architecture in `E:\Unity Clicker Genesis Documentation\Save-System-Design.md` (written by the parallel indexing session, implemented here nearly verbatim against the real field list): a local JSON file at `Application.persistentDataPath` (not PlayerPrefs — wrong tool for nested data), a sectioned `SaveData` class, mandatory `saveVersion` + a migration-chain pattern from day one, atomic temp-file-then-rename writes plus a `.bak` fallback, save-on-pause/quit, and a light-obfuscation-not-real-encryption posture (explicitly flagged as NOT anti-cheat — real save encryption is layer 2). The original 2026-08-06 elaboration's fuller vision (social login, cloud save, real encryption/signing) is preserved as "layer 2," not dropped — implemented behind a real `ISaveStorage` interface seam so it's additive later, not a rewrite.
  - **New `Assets/Scripts/Save/` folder:** `SaveData.cs` (root `SaveData` + `EconomyState`/`ProgressionState`/`PrestigeState`/`BookScribeState`/`TierSubmanagerState`/`BookProgressEntry`/`SkillRankEntry` — settings deliberately excluded, since `GameSettings` already persists independently via PlayerPrefs and duplicating it would just create a second source of truth), `ISaveStorage.cs`, `LocalFileSaveStorage.cs` (temp-file-then-`File.Replace` atomic swap with a delete+move fallback for platforms where `File.Replace` isn't reliable, `.bak` written before every overwrite, base64+XOR obfuscation, try/catch-wrapped load that falls back primary→backup→fresh `SaveData` on any failure), `SaveMigrator.cs` (`CurrentVersion=1`, no real migrations yet — scaffolding only, ready for the next data-model change).
  - **Real field list, enumerated by walking the live classes (not guessed):** `InkWallet` (balance/LifetimeEarned/TotalSpent), `LevelSystem` (TotalXp/CurrentLevel), `PrestigeSystem` (Grace/GraceEverSpent/FreePrestigeCount/ResetPrestigeCount), `PrestigeSkillSystem` (its private `Dictionary<string,int> ranks`, exported as a list-of-pairs since `JsonUtility` can't serialize `Dictionary<>`), `ScribeSystem` per registered book (owned[]/managerUnlocked[]/submanagerOwned[][], also list-of-pairs-shaped for the nested bool array), `GameLoopController.ClickPowerLevel`/`ProgressMultiplier`, and every book's `BookProgress` (not just the active one — switching books never resets another book's progress, so the save has to cover all of them). Each of the five state-owning classes got a matching `LoadState(...)` method (`ScribeSystem` got `ExportOwned`/`ExportManagerUnlocked`/`ExportSubmanagerOwned`/`ImportState`, length-bounded against the CURRENT config rather than trusting saved array lengths, so a roster that's grown since the save was written — e.g. more submanagers added to a book — still loads correctly).
  - **`GameLoopController` orchestration:** `CaptureSaveData()`/`ApplySaveData(SaveData)` (the walk-every-system round trip), `SaveGame()`/private `LoadGame()`, called from `Awake()` right after the existing default-state bootstrap — a fresh install's loaded `SaveData` comes back with an empty `activeBookResourceId` (the C# default), which `LoadGame()` treats as "nothing to apply," leaving a new player's just-built Genesis-at-verse-0 state alone rather than stomping it with an empty save. `OnApplicationPause(true)`/`OnApplicationQuit()` both force an immediate synchronous save (Android has no guaranteed quit event); `Update()` also debounces a 30-second periodic autosave on top of those, per §6's "most robust but most I/O" tradeoff reasoning.
  - **Verified live, real end-to-end round trip:** entered Play, added Ink, bought 5 verses, bought 2 scribes, bought a Click Power upgrade, tapped once, called `SaveGame()`, confirmed a `50000`-Ink-plus-taps state; exited Play (Editor Play-mode stop does NOT fire `OnApplicationQuit` — confirmed this is why the explicit `SaveGame()` call in the test mattered, not a fallback the real build can rely on skipping); re-entered Play, confirmed every discrete counter (`TotalSpent`, `NextVerseIndex`, `ClickPowerLevel`, scribe owned count, `Level`, `TotalXp`, `ActiveBookResourceId`) matched exactly, while `Balance`/`LifetimeEarned` were correctly slightly HIGHER than the saved snapshot (passive Ink/sec kept ticking during the seconds between reload and the check — expected, not a bug). Also verified the corruption-recovery path directly: hand-corrupted `save.json` with the real backup intact → `Load()` recovered from `.bak` correctly; corrupted BOTH files → `Load()` returned a fresh `SaveData` with no exception thrown, per §5's explicit design call. Confirmed the on-disk file is genuinely obfuscated (not raw-readable JSON) and that the `.tmp` file never survives past a completed save (atomic swap working). Test save files deleted from `Application.persistentDataPath` afterward so the user's own next Play session starts clean, not from synthetic test data.
  - **Same placeholder-pending-playtesting caveat does NOT apply here** — this is real infrastructure, not a tunable game-balance number; nothing about it needs revisiting after real playtesting the way Ink costs/XP curves do.

- **Prestige (CONFIRMED FULL SPEC 2026-08-03, BUILT 2026-08-05):** benchmarked against genre convention (Cookie Clicker, AdVenture Capitalist, Clicker Heroes, Egg Inc) before finalizing. Full spec lives on the Notion "Progression" subpage — summary (built behavior noted where it diverges from the original paper spec):
  - **Trigger:** reaching `prestigeLevelThreshold` (placeholder = 5), via a "Skill Tree" button on ClickerScreen (renamed from "Prestige" 2026-08-05 — the button only opens the Grace Skill Tree screen, where the actual Prestige/Reset choice is made, it doesn't itself prestige anything). Stays visible once the player has ever prestiged (`PrestigeCount > 0`), independent of level, so a level reset can never hide the only way back to spend Grace (real bug, fixed 2026-08-05). **Frequency:** no cooldown on the reset path (every reset cycle requires re-reaching the threshold again, since it resets Level/XP) — the free path does NOT reset Level/XP (REVISED 2026-08-05, explicit user correction — originally built to reset on every path, which stranded players with unspendable Grace once the button hid itself). **Currency:** single currency, "Grace," for v1.
  - *Default (free):* awards Grace = `floor(sqrt(LifetimeInkEarned)/50) + 10 + floor(versesUnlocked/5) + chaptersCompleted×2 + booksCompleted×10`. Nothing is lost — full Ink, upgrades, Level/XP, and all unlocked verses stay exactly as they are.
  - *Optional reset (opt-in):* player may voluntarily wipe Ink balance, Click Power level, scribe owned counts, AND Level/XP back to baseline for **2.5x** normal Grace.
  - **Hard rule, both paths:** a reset NEVER re-locks or removes verses already unlocked, and never touches Grace Skill Tree node ranks (permanent). Only numeric progress (Ink, upgrade levels, Level/XP on the reset path) can reset — never delivered scripture content or tree progress.
  - **Grace spending — real Grace Skill Tree (BUILT 2026-08-05, supersedes the lean-v1 flat-cost plan)**: 105 nodes across 9 branches, reached via the Skill Tree screen (`PrestigeScreen.unity` + `PrestigeScreenUI.cs`). 8 economy branches (Ink Flow, Steady Hand, Overseer's Wisdom, Illuminated Pages, Scribe's Diligence, Grace of Memorization, Swift Unlock, Manager's Calling), each an 8-node chain (3× rank-1 filler, 2× rank-3, 2× rank-5, 1× rank-1 capstone), wired into the real economy math via `GameLoopController.EffectiveInkPerSecond`/`EffectiveTapAmount`/pricing/Grace-preview/`EffectiveManagerLevel`. A 9th Book Progression branch unlocks the 38 remaining OT books individually (canonical order) plus a 3-node New Testament gate cluster (Gospel Threshold → Apostolic Path → Revelation's Veil, steep Grace cost, real-money alternative planned but not wired). Radial layout: branches as spokes from a central "Grace" hub, connecting lines, per-branch icon theming (Homeless/Item_Icons pack), zoom in/out, node brightness tracks OWNERSHIP not just prerequisite-unlock (a node stays dark until at least rank 1 is actually bought, regardless of whether its prerequisite is satisfied — real user correction 2026-08-05, first pass conflated "available to buy" with "already lit"). Full branch/node detail in the offline doc folder's Grace-Skill-Tree.html. The old automatic "+1% Ink per Grace ever spent" auto-bonus is removed (superseded, not stacked).
  - **Visual polish + layout redesign pass (2026-08-05, same day as the initial build).** Header/chrome themed to match every other screen: Pause button got the real gear-icon sprite (was plain text "Menu"); Grace readout got a dark background panel (was unreadable floating text); Prestige/Reset/Back header buttons got the same wooden sprite as everywhere else; Back button shrunk to a small "<" icon with a "Back" hover tooltip; skybox set to match. **Book Progression branch layout rebuilt** (user's explicit correction — the original build gave it a 9th spoke slot among the economy branches with a per-node angular-drift hack to fake a spiral arm, which read as "the books of the bible just kinda curve up to the right and then to the left... nodes are too close to each other, can't even read the descriptions"): now a full outer ring at a fixed radius outside the economy wheel's reach, all 41 book/gate nodes spread evenly across 360° and connected in canonical order, framing the 8 economy spokes like a wheel's rim — economy branch spacing also widened (base radius 220→320, ring step 150→210) so neighboring branches' labels stop overlapping. **Zoom In/Out buttons** were built with a broken sprite path (missing the double space in `UI board Small  stone.png` — this asset pack's filenames are inconsistently spaced, a recurring trap) that silently fell back to Unity's default white sprite with no glyph at all; fixed the path and added real "+"/"-" labels, since the buttons never had any text on them to begin with.
  - **Two new UX features (2026-08-05, user's own ideas).** A persistent **description box** sits between the Grace readout and the tree — hovering any node (even locked/unaffordable ones) shows its description there instead of relying on a floating tooltip aimed precisely at a small circle; every other button on the screen still uses the regular floating tooltip. Clicking a node no longer spends Grace instantly — a themed **Yes/No confirmation popup** shows the exact rank and cost first ("Buy Ink Flow I (rank 1/1) for 5 Grace?") before anything is spent.
  - We deliberately diverge from every genre example here: they all wipe everything except the prestige currency on reset. Ours never touches unlocked verses on either path — mission-driven adaptation, not a gap.
  - **Progressive node VISIBILITY, not just brightness (CONFIRMED 2026-08-06, NOT YET BUILT — real correction/addition to the built behavior above).** The existing "brightness tracks ownership" fix (bug #97) only handles nodes the player can already SEE. What's still missing: unowned nodes shouldn't render at all until their prerequisite is owned - not grayed out, not visible-but-locked, literally not drawn. Mechanic, in the user's own words: buying Core reveals only the very first node on each of the 9 spokes/ring-start - nothing else. Buying that first node reveals the next node after it (still locked/grayed until affordable or bought), and so on down each branch. The point is players never see the tree's full scale up front - if more nodes get added in a future update, it reads as "there's suddenly 5 more skills" rather than "the tree always looked like this." Needs a real change to `PrestigeScreenUI`'s tree-building/rendering logic (currently draws every node from the config at once); connecting lines presumably need the same treatment (a line to a not-yet-revealed node shouldn't draw either). Scoped as its own follow-up, not started.
- **Per-book currency/theming:** phased. v1 = single shared Ink, cosmetically reskinned per book (color/label only, e.g. "Genesis Ink"). v1.x/v2 = real separate non-transferable per-book currencies + unique clicker sets. Don't build the full N-economy system until the base loop is proven.
- **Translations (v1):** KJV only. NIV and Amplified are explicitly on hold/deferred to a future update (confirmed 2026-07-31) — not a pending decision to chase, not being built around at all right now. Revisit licensing when that update is actually scoped.
- **Versioning:** `X.Y.Z` — X = official release marker (0 = pre-release), Y = feature/update bump (whether or not shipped live), Z = patch/bugfix only. Log changes in the Notion Changelog subpage.
- **GitHub Release naming convention (standardized 2026-08-06 — all past release titles renamed to match, per user's explicit ask "we need a set way of doing it").** Tag: `vX.Y.Z` (unchanged, already consistent). Title: `Clicker Genesis vX.Y.Z — <short highlight> (<platform(s)>)` — e.g. `Clicker Genesis v0.3.3 — Managers/Support tab redesign, first Mac build (Windows + macOS)`. The short highlight is the single biggest thing in that release, not a full changelog (full detail goes in the release body). Platform suffix lists every platform actually built for that release — `(Windows desktop)` for the six pre-0.3.3 Windows-only releases, `(Windows + macOS)` starting v0.3.3 once Mac Build Support was installed. Apply this to every future release, not just when asked.
- **macOS builds (added 2026-08-06):** Mac Build Support module installed in this machine's Unity Hub. Builds are cross-compiled from this Windows machine and are unsigned/unnotarized (no Apple Developer account/Mac hardware in this pipeline) — macOS Gatekeeper will block the first launch, the user needs to right-click → Open (or clear the quarantine flag) once per install. This is expected for an indie unsigned build, not a bug to fix. Flag this in every Mac release's notes so it isn't mistaken for broken packaging.
- **Real gotcha hit 2026-08-06/07: installing a new platform module (Mac Build Support) does NOT work in the same Editor session without a restart.** `BuildPipeline.IsBuildTargetSupported(...)` and `EditorUserBuildSettings.SwitchActiveBuildTarget(...)` both report success/true immediately after a fresh module install, which is misleading — the actual player build gets through asset compilation fine but then throws `UnityException: Build target 'StandaloneOSX' not supported` at the `PostprocessBuildPlayer.Postprocess` step specifically, because the running Editor process still has the old (pre-module) native postprocessing pipeline loaded in memory. No output is written (`Builds/Mac/` never gets created) despite `BuildPipeline.BuildPlayer`'s own report sometimes claiming `Result: Succeeded`. Fix: the user must fully restart the Unity Editor after installing a new platform module before that platform's builds will actually work — don't trust the support-check APIs alone as proof a freshly-installed module is build-ready.

## Real mobile-device layout bugs found + partially fixed (2026-08-09, v0.4.0)
User tested the build on a real Android device (Galaxy S25 Ultra) for the first time and found the portrait UI badly broken — not the Editor Game view issue Bug #58 was originally caught from, a genuinely different failure mode confirmed via 11 real device screenshots.
- **Root cause #1, confirmed via direct `.unity` inspection:** three screens (`SettingsScreen`/`ClickerScreen`/`BuyVerseScreen`) had their `CanvasScaler` reference resolution hardcoded to a LANDSCAPE `1920x1080` pair while rendering on a portrait phone. **Root cause #2, the real reason even the one already-portrait screen (MainMenu, `1080x1920`) still broke:** a real device's aspect ratio never exactly matches whatever single static reference was authored against (the S25 Ultra's real `1080x2340` is notably taller than `1080x1920`), so `CanvasScaler`'s width/height blend produces dead space or edge-clipping depending on which dimension the mismatch favors — a static reference resolution, portrait OR landscape, can never be "the fix" once the same UI has to render across an unknown range of real device aspects and support live rotation.
- **Fix: new `ResponsiveCanvasController.cs`** (`[RequireComponent(typeof(CanvasScaler))]`), added to the Canvas GameObject on MainMenu/Settings/Clicker/BuyVerse/AchievementScreen (PrestigeScreen deliberately skipped — real uncommitted changes there from a concurrent session's active Skill Tree redesign, avoided touching it to not collide). Recomputes `referenceResolution` live off `Screen.width`/`Screen.height` every time it actually changes (cheap per-frame check, not a rebuild — same "no bug-#22-class per-frame cost" discipline as everywhere else) instead of a static per-scene value. New `GameSettings.Orientation` (`OrientationPreference` enum: Auto/Portrait/Landscape, PlayerPrefs-persisted, default Auto) drives both the reference-resolution choice and Unity's own `Screen.orientation` lock on mobile (`GameSettings.IsOrientationLockSupported` gates this to Android/iOS only — desktop's OS owns window rotation). The underlying auto-rotate-follows-device logic is fully built; the actual Settings-screen toggle UI for it is not (tracked, not yet done).
- **Root cause #3, the worst reported bug, genuinely unreadable text-on-text overlap in every list row (Scribe/Manager/Support/Verse/Chapter):** NOT a scaling issue at all — `ScribeListUI`'s shared `RowTemplate` had its `Desc` text box anchored **full-stretch** (`anchorMin (0,0)` to `anchorMax (1,1)`), literally overlapping `Name`'s box at the top of the row; `BuyVerseScreenUI`'s `VerseRowTemplate` had `Reference`/`Cost` as non-auto-sizing fixed-font text that wrapped to 2-3 lines inside a fixed 70px-tall row, spilling into the next row. ## ASV, WEB, and OSHB (Hebrew interlinear) verse extraction (2026-08-09, data ready, NOT wired into the game)
User asked to add three more translation sources after a licensing-status research pass ruled out NIV/Amplified/NKJV entirely (all three are 20th-century copyrighted works with no earlier public-domain edition to fall back to — unlike KJV→NKJV or Reina-Valera 1909→1960, neither NIV's 1973/1978 first edition nor Amplified's 1954/1958 first edition was ever public domain, so there's no "older version" loophole for either). Confirmed genuinely public-domain instead: **ASV** (American Standard Version, 1901), **WEB** (World English Bible, a modern-English CC0/public-domain update of the ASV), and **OSHB** (Open Scriptures Hebrew Bible — the Westminster Leningrad Codex tagged word-by-word with Strong's numbers and morphology).
- **Real technical win over the Geneva/Ethiopian extraction:** unlike those two (scanned PDF/docx sources needing font-encoding archaeology), ASV/WEB/OSHB are all clean, already-structured digital sources with direct internet access working from this sandbox (`curl` succeeds). ASV/WEB came from eBible.org's verse-per-line (`_vpl.zip`) plain-text format (`BOOKCODE CHAPTER:VERSE<tab>text`, one line per verse) — trivial to parse, no OCR-style cleanup needed. OSHB came from the [openscriptures/morphhb](https://github.com/openscriptures/morphhb) GitHub repo as OSIS-format XML, one file per book, word-level `<w lemma="..." morph="...">` tags.
- **Extracted and validated:** ASV — 66/66 standard-canon books, 31,102 verses, matches the KJV canonical outline exactly (0 mismatches). WEB — 81 books (66 standard canon + 15 Apocrypha/Deuterocanon the source includes between Malachi and Matthew: Tobit, Judith, Esther-Greek, Wisdom, Sirach, Baruch, 1-4 Maccabees, 1 Esdras, Prayer of Manasseh, Psalm 151, 4 Ezra, Daniel-Greek), 38,058 verses total. **One real, flagged (not "fixed") textual-tradition difference found:** WEB places the Romans doxology (16:25-27) at the end of chapter 14 instead of chapter 16 — a well-documented manuscript-versification variant, not an extraction bug, same category of finding as Ethiopian's Ezra matching the 1 Esdras tradition. OSHB — 39/39 Old Testament books, 23,213 verses (Hebrew/Masoretic versification legitimately differs from KJV's English versification in several places — e.g. Hebrew Psalm superscriptions often count as verse 1, shifting everything after — not reconciled to match KJV, since the whole point is showing the original structure), 306,785 individually-tagged Hebrew words. Spot-checked Genesis 1:1 directly against the known Masoretic text: exactly 7 words, correct Strong's numbers (7225=beginning, 1254=create, 430=God/Elohim, 853=untranslated direct-object marker, 8064=heavens, 776=earth) — confirmed accurate, not just structurally parsed.
- **Licensing note, distinct from the verse text itself:** the underlying Westminster Leningrad Codex Hebrew text is Public Domain, but the OSHB *tagging layer* (the word-level Strong's/morphology data specifically) is licensed **CC BY 4.0** (attribution required, not pure public domain) per its own repo. Needs an Assets & Credits entry once wired into the game, same as every other third-party asset in this project.
- **Output schema:** ASV/WEB match the existing KJV/Geneva/Ethiopian schema exactly (`{bookName, translation, chapters:[{chapterNumber, verses:[{verseNumber, text}]}]}`) at `Assets/Resources/Verses/ASV/*.json` and `.../WEB/*.json`. OSHB uses a necessarily different, richer per-verse shape (`{bookName, translation:"OSHB", language:"Hebrew", chapters:[{chapterNumber, verses:[{verseNumber, text (plain concatenated Hebrew), words:[{text, strongs, morph}]}]}]}`) at `Assets/Resources/Verses/OSHB/*.json`, since it's word-tagged Hebrew, not a flat English verse translation.
- **Explicitly NOT done, and a real open design question for OSHB specifically (flagged, not decided unilaterally):** none of these three are wired into any game system yet, same "prep work only" status as Geneva/Ethiopian. ASV and WEB slot in cleanly as additional selectable translations, same shape as KJV/Geneva/Ethiopian. **OSHB is structurally different and needs a real decision before it can be treated the same way** — it's untranslated Hebrew with Strong's/morphology tags, not an English reading translation on its own, so it doesn't obviously fit the existing "player unlocks and reads verses in a chosen translation" core loop the way the others do. Two real directions, not decided: (a) treat it as its own full selectable "translation" anyway (Hebrew-only, presumably paired with a forced interlinear gloss display so it's actually readable), or (b) build it as a study/interlinear *overlay feature* layered on top of an existing English translation (show the Hebrew word + Strong's number + gloss alongside/under the English text a player has already unlocked) — closer to what "interlinear" usually means and closer to the user's original stated want. Don't build UI for this without the user picking a direction first.

- **Added 2026-08-09, same session: Reina-Valera 1909 (RV1909, Spanish).** Confirmed public domain (unlike the far more commonly used RV1960 revision, which is copyrighted by the United Bible Societies/American Bible Society — same "old edition PD, later revision copyrighted" shape as NKJV). Same eBible.org verse-per-line source pipeline as ASV/WEB: 66/66 books, 31,102 verses, 0 mismatches against the canonical KJV outline. Output at `Assets/Resources/Verses/RV1909/*.json`, same schema as ASV/WEB/KJV. Real Spanish text confirmed directly (Genesis 1:1 reads "En el principio crió Dios los cielos y la tierra" — genuine period-appropriate 1909 wording, not a placeholder). This is the first non-English translation source in the project — opens the door for the "include other languages like Spanish" goal, though (like every other translation here) it's extracted data only, not wired into any book-picker/language-selection UI yet.

- **Added 2026-08-09, same session: Webster Bible (1833, Noah Webster's own revision of the KJV).** Confirmed public domain (pre-1930, and Webster's revision was always his own — no separate "modern re-copyrighted edition" trap the way NKJV/RV1960 have). Same eBible.org pipeline as ASV/WEB/RV1909: 66/66 books, 31,102 verses, 0 mismatches against the canonical KJV outline (expected, since it's a light Webster-era language cleanup of the KJV rather than a fresh translation — Genesis 1:1 reads identically to KJV: "In the beginning God created the heaven and the earth"). ## Android vs. desktop: separate scene files (2026-08-13, real architecture decision)
User's own diagnosis, confirmed correct: every production scene (`ClickerScreen.unity`, `MainMenu.unity`, etc.) was a single shared `.unity` file that Windows, Mac, Linux, AND Android all built from. So an Android-motivated layout tweak (button repositioned for a touch/phone screen) was baked into the *only* copy of that scene — which is also what the desktop builds read — and vice versa. This is a different failure mode from the landscape-only decision below (that was one scene serving two ORIENTATIONS; this is one scene file serving two PLATFORMS with different UI needs even at the same orientation), but the same root shape: one shared scene asset can't cleanly serve two audiences with different layout needs.
- **Fix: `Assets/_ScenesAndroid/` — a full duplicate of all 11 production scenes** (MainMenu, ClickerScreen, BuyVerseScreen, SettingsScreen, PrestigeScreen, AchievementScreen, CreditsScreen, StatsScreen, StoreScreen, SaveSlotScreen, NewGameSetupScreen — `CoreLoopTest`/`SampleScene` deliberately excluded, dev/test scenes not part of the shipped flow). Same scene names as their `Assets/_Scenes/` counterparts, own independent GUIDs (verified distinct after import, not aliases) — this means `SceneTransitioner`/`SceneNavButton`/every `LoadScene("ClickerScreen")` call needed ZERO code changes, since which physical scene asset gets used is determined entirely by which folder's scenes are fed into `BuildPlayerOptions.scenes` at build time, not by the scene name.
- **`Assets/Editor/BuildScripts.cs`** (new, persisted for real — earlier builds this session used one-off `script-execute` calls, not worth re-typing every time): `Tools/Build/{Windows,macOS,Linux,Android}` menu items, all real methods callable via script-execute too. Windows/Mac/Linux read the shared `EditorBuildSettings.scenes` list (`Assets/_Scenes/*`, unchanged). **Android reads a hardcoded `Assets/_ScenesAndroid/*` path array instead** — deliberately NOT reading `EditorBuildSettings.scenes`, since Unity's global Build Settings list is single/shared and can't hold two different scene sets at once. Every build uses `BuildOptions.CleanBuildCache` per the existing standing rule (a stale incremental cache was found 2026-08-11 to silently ship a build missing months of work).
- **Standing rule going forward, exactly as the user framed it:** any layout-affecting change made to a desktop scene (`Assets/_Scenes/X.unity`) must be manually mirrored into its Android counterpart (`Assets/_ScenesAndroid/X.unity`) as part of the same task — don't treat it as a follow-up, don't assume "it's basically the same" is good enough. Conversely, an Android-only layout fix should NOT touch the desktop scene at all now — that was the entire point of the split.
- **Real, accepted tradeoff, not hidden:** this doubles the scene-maintenance surface (11 scenes → 22) and creates real drift risk if the mirroring rule above isn't followed — logic-only changes (new C# behavior on a `MonoBehaviour`, a new manager method) don't need mirroring since script assets aren't duplicated, only the two scene-file trees are; it's specifically RectTransform/layout/prefab-instance edits inside a scene that need the manual mirror.
- **Not yet done:** no Android-specific layout tweaks have actually been re-applied yet — the `_ScenesAndroid` copies are currently byte-for-byte identical content to their desktop counterparts (just independent GUIDs). The next Android-focused session should make its layout fixes directly in `_ScenesAndroid`, not in `_Scenes`.

## Standing rule: TextBTN wood-button text/icon vertical alignment (confirmed 2026-08-11)
