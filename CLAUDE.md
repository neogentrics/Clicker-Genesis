# Clicker Genesis — Project Context

Bible-verse idle/incremental clicker for Android (Unity, URP 3D Core template). Goal: help players learn and memorize scripture through play. Micro-transactions exist but are never required for progress or content.

**Full design doc (source of truth, keep it updated as design evolves):** https://app.notion.com/p/3aead37812e881c99578d596f3a29921 — 11 subpages: Core Loop & Economy, Progression, XP & Leveling, Scribes & Managers, Sound & Audio System, Art & UI Direction, Translations, Future Systems & Idea Backlog, Assets & Credits, Open Questions & Status, Project Setup & Tech, **Changelog** (full version-by-version build history, `<details>` toggles per version), Bug Tracker.

## Guiding principle
Scripture text is never altered, paraphrased, or reinterpreted. Only unedited, recognized translations are used. This constraint overrides convenience in any implementation decision.

## Confirmed design (do not re-litigate without the user explicitly reopening it)

- **Currency:** Ink. Earned by tapping and by passive/idle upgrades ("scribes").
- **Core action:** spend Ink to buy the *next* verse in canonical order within your active book (no skipping within a book in v1). Buying reveals verse text + reference.
- **Screen split (2026-07-31):** tapping and buying are separate screens — a Clicker screen (tap-for-Ink only) and a Buy Verse screen (spend Ink, verse reveal), navigated via a button.
- **Chapter bulk-buy:** sum of remaining verse costs in the chapter × 0.75 (25% discount).
- **Pricing curve:** `verse_cost(n) = base_cost × growth_rate ^ n`, `n` resets per book. `base_cost`/`growth_rate` are data-driven (ScriptableObject fields), never hardcoded — placeholder pending playtesting, same as every other numeric constant in this project.
- **XP/Leveling:** content-completion based (verse/chapter/book), not RPG/combat based. `XpConfig`: xpPerVerse=1, xpPerChapterBonus=10, xpPerBookBonus=100 pre-first-reset; after a player's first Reset-Prestige these permanently become 10/25/150. Level threshold: XP for L→L+1 = `levelXpBase * L` (levelXpBase=50). `prestigeLevelThreshold`=5. All placeholder pending playtesting.
- **Book unlocking:** player picks ONE starting book free on first run. Locked into that book until prestige-eligible (level threshold, reachable mid-book). Post-prestige book choice is free-pick within the currently-unlockable pool (via the Grace Skill Tree's Book Progression track).
- **Testament scope (v1):** Old Testament only is exposed in gameplay. `CanonicalBookOrder.Books` lists only the 39 OT books — this is deliberate, not incomplete: all 66 books' scribe/manager data exists and is wired (`scribeSystemsByBook`), but there's no code path to switch into or unlock an NT book yet. Books tab shows a static "New Testament — Coming Soon" row. See OT→NT transition design under Open Questions.
- **Clicker/Manager subsystem:** standard idle-game shape. "Scribes" = passive Ink/sec generators bought on an escalating curve, one roster per book (icons/costs/output are data-driven `ScribeSetConfig` ScriptableObjects, not hardcoded per-book C#). "Managers" = one per scribe type, gated by BOTH player level AND an Ink cost (first manager per book stays free once level-eligible — same "personalization hook" pattern as the free starting book). "Support" = submanagers (minor characters) attached to a manager, boosting cost or output, own tab. Scribes/Managers/Support tabs show only the ACTIVE book's roster, but every registered book's scribes keep producing Ink simultaneously in the background regardless of which is displayed.
- **Full 66-book Bible content buildout is DONE.** Every OT (39) and NT (27) book has a real, schema-validated scribe/manager/submanager roster (`Assets/Config/*Scribes.asset`), each authored from the Bible Character Index data (`Assets/Resources/Bible/CharacterIndex/*.json`) with real computed verse indices (not placeholder positions) — manager unlocks correctly gate on a character's own real first-appearance/key-event verse. Tiers are typed `Person` (a named character manager) or `Law` (theme/teaching content for law-heavy books like Leviticus, with an optional `deliveredByManagerId` attribution that degrades gracefully to no line if that person has no Person tier in that book). Genesis was the hand-authored pilot/template; the rest were produced via a Workflow-based multi-agent pipeline once the pattern was proven. Full detail/design rules (law-vs-person test, naming-collision discipline, Jesus-gets-independent-tier-per-Gospel) in the Notion Scribes & Managers subpage and Changelog.
- **Art direction (2026-07-31):** two-layer system. Base UI = warm parchment & minimal ink (calm, legible, mobile-fast, ~95% of the time). Accent layer = stained-glass *technique* (jewel-tone blocks, dark linework, glow) reserved for reward moments only (verse reveal, chapter/book complete, prestige, the Store screen) — explicitly NOT literal cathedral imagery.
- **Save system (BUILT, then superseded by a 3-slot system, 2026-08-08):** local JSON at `Application.persistentDataPath` via `ISaveStorage`/`LocalFileSaveStorage` (atomic temp-file-then-rename + `.bak` fallback, light obfuscation not real encryption — real encryption is an explicit "layer 2," not built), `SaveMigrator` with a version-chain pattern. Main Menu has separate New Game / Continue flows; New Game (first time on a slot only) walks the player through translation (KJV only for now) then starting book. Achievement ledger (`achievements.json`) is deliberately GLOBAL and independent of save slots — completing content on one slot is visible from a fresh slot.
- **Testament-based color theme switch (CONFIRMED 2026-08-07, NOT YET BUILT):** switching active book into the NT should re-theme the whole UI to a distinct second palette (ClickerScreen, BuyVerseScreen, Settings, Pause Menu, etc.) — explicit exception: the Skill Tree screen is NOT re-themed, it's a shared cross-Testament system. Specific NT palette not decided.
- **Landscape-only, single reference layout (2026-08-12, supersedes the old "auto-detect mobile vs desktop and reflow portrait/landscape" requirement).** Unity's `CanvasScaler` can't correctly serve one scene in both orientations at once — the app is now locked to landscape at the OS level (`allowedAutorotateToPortrait`=false) rather than live-rotating. `ResponsiveCanvasController` recomputes `referenceResolution` live off real screen size and uses `matchWidthOrHeight = 1.0` (match-height, fixed 2026-08-15 — 0.5 blend was the real root cause of the long-standing "resolution change misplaces buttons" bug, verified 0 vertical drift across 7 real device aspect ratios). Known limit: a screen narrower than 16:9 (4:3 tablet) still loses horizontal canvas units — check before any tablet release. Built-but-inert `Portrait*` reflow components remain in the project unused, harmless scaffolding.
- **Prestige (full spec BUILT 2026-08-05, Skill Tree rebuilt as "SkillTreeV2" 2026-08-09):** trigger = reaching `prestigeLevelThreshold` via a "Skill Tree" button (stays visible once `PrestigeCount > 0`, independent of level). Single currency "Grace" for v1. *Free path:* awards Grace by formula, nothing is lost. *Optional reset path:* wipes Ink/Click Power/scribe counts/Level-XP for 2.5x normal Grace. **Hard rule, both paths:** unlocked verses and skill-tree ranks are NEVER lost — only numeric progress can reset. **Current tree = SkillTreeV2**, a fog-of-war constellation UI (nodes + connector lines fully hidden, not just dimmed, until a prerequisite is owned) — a central Convergence node gates a Book Progression menu opening per-book Mastery sub-trees. Wired to the real `PrestigeSystem.Grace` balance; bonuses stack additively with the old (deprecated-but-not-deleted, `PrestigeScreenUI`/`PrestigeSkillTreeGenerator`) 105-node radial tree across all 8 effect types. All 146 nodes have real authored OT content (the 8 economy branches + Core + Convergence + all 39 OT books' Book Progression/Mastery). **The deeper "real per-book branch redesign"** (skills tied to specific books with cross-skill dependencies, described under Open Questions) is NOT what this rebuild did — SkillTreeV2 ported the existing 8-branch shape onto new rendering + real content; the structural redesign is still open.
- **Per-book currency/theming:** phased. v1 = single shared Ink, reskinned per book (color/label only). v1.x/v2 = real separate non-transferable per-book currencies — don't build until the base loop is proven at scale.
- **Translations (v1 gameplay):** KJV only is wired into the game. Six more have been extracted/validated as data but are NOT wired into any gameplay system yet: Geneva 1560, Ethiopian (both with full Character Index rosters too, 231 book-translations total), ASV, WEB, RV1909 (Spanish), Webster. OSHB (Hebrew interlinear, word-tagged) is extracted but needs a real design decision before it can be treated like the others (see Open Questions). NIV/Amplified/NKJV/RV1960 are permanently ruled out — all are still-copyrighted 20th-century works with no public-domain earlier edition to fall back to.
- **Versioning:** `X.Y.Z` — X = official release marker (0 = pre-release), Y = feature bump (only bumps once the user confirms the current feature set is genuinely playable end to end — not just because a feature-shaped chunk of code landed), Z = patch/bugfix. **Alpha/Beta split (2026-08-09):** every release before v0.4.1 is retroactively Alpha; v0.4.1 onward is Beta. Log every change in the Notion Changelog subpage AND the offline `Changelog.html`.
- **GitHub Release naming (standardized 2026-08-06):** tag `vX.Y.Z`. Title: `Clicker Genesis vX.Y.Z — <short highlight> (<platform(s)>)`, e.g. `Clicker Genesis v0.4.6 Beta — Landscape lock, font selector (Windows + macOS + Linux + Android)`. Every release ships every platform actually built for it, listed in the title. **Standing rule (2026-08-06):** every future release must ship builds for every supported platform, all attached to the same GitHub Release.
- **macOS builds:** cross-compiled from Windows, unsigned/unnotarized (no Apple Developer account) — Gatekeeper blocks first launch, user right-clicks → Open once. Expected, not a bug; flag it in every Mac release's notes.
- **Real gotcha:** installing a new Unity platform module (e.g. Mac/Android Build Support) does NOT take effect in the same Editor session — `BuildPipeline`/`EditorUserBuildSettings` APIs report success immediately but the actual build throws at the postprocess step because the running Editor still has the old native pipeline loaded. **Restart the Editor after installing a platform module before trusting a build from it.**
- **Android vs. desktop use separate scene files (2026-08-13).** `Assets/_ScenesAndroid/` mirrors all 11 production scenes in `Assets/_Scenes/` with independent GUIDs — `SceneTransitioner`/`LoadScene(name)` calls need zero code changes since which physical asset gets used is determined by which folder feeds `BuildPlayerOptions.scenes` at build time (`Assets/Editor/BuildScripts.cs`, `Tools/Build/{Windows,macOS,Linux,Android}` menu items — Android reads a hardcoded `_ScenesAndroid` path array, NOT `EditorBuildSettings.scenes`). **Standing rule: any layout-affecting change to a desktop scene must be manually mirrored into its Android counterpart in the same task, and vice versa — logic-only C# changes don't need mirroring, only RectTransform/layout/prefab-instance edits inside a scene file.** Every build must use `BuildOptions.CleanBuildCache` (a stale incremental cache has silently shipped outdated builds at least twice — see Working Style Notes).
- **Standing UI rule: TextBTN wood-button text/icon vertical alignment (confirmed 2026-08-11).** Every button using a `TextBTN_Medium`/`TextBTN_Big` sprite (Fantasy Wooden GUI Free) has its face raised with a shadow band along the bottom ~20% of the sprite — centering a Text/Icon child at `anchoredPosition.y = 0` visually sinks it into the shadow. **Fix: set `anchoredPosition.y = buttonHeight * 0.10f`** on the Text/Icon child for every new `TextBTN`-sprite button going forward.

## Open questions (ask the user, don't guess)

- **OSHB (Hebrew interlinear) integration direction — real decision needed, user wants to read the actual data first.** Two directions on the table: (a) its own selectable Hebrew-only translation with a forced interlinear gloss, or (b) a Strong's/gloss overlay feature on top of an existing English translation the player already unlocked. Don't build either without the user deciding.
- **Grace Skill Tree structural redesign (per-book branches, real cross-skill dependencies, NT thematic branches) — real user vision, NOT the SkillTreeV2 rendering rebuild described above.** User wants: a real Grace cost rebalance at scale; skills tied to SPECIFIC books (not one shared tree ignoring which book is active); cross-skill dependencies beyond simple prerequisite chains (needing multiple specific skills, a specific manager owned, or a specific verse unlocked); future NT thematic branches (fruits of the Spirit, seven deadly sins, spiritual warfare) — explicitly deferred pending the user's own research. Scale is deliberate ("massive... on purpose") but don't build ahead of the content it needs to hang off of. **Do not start this without a real design conversation with the user first.**
- **OT→NT transition system — designed in conversation, NOT built.** Two separate Skill Trees (not one mega-tree); NT uses its own currency, NOT shared Grace (prevents "Grace farming" the easier OT side), with an optional steep one-way OT-Grace→NT-currency conversion planned; Ink and the future Talents currency stay shared across both Testaments; transition gate = OT 39/39 complete AND a level/prestige threshold (needs an achievement-adjacent design conversation that hasn't happened); OT Skill Tree stays fully open/spendable after moving to NT. NT tree structure itself is on hold pending the user's thematic-branch research (see above).
- **Store & Talents currency — mechanics + a visual design brief exist (Notion Future Systems & Idea Backlog subpage), ZERO in-engine implementation.** Third currency confirmed named "Talents". Real next build task once the Skill Tree redesign direction is settled (or in parallel, if prioritized). Core pattern: purchasable rows can carry a second Talents-paid button alongside Ink/Grace, built in from the start; every Talents-gated unlock must stay reachable through normal play too, per the IAP-never-required guiding principle.
- **Main Menu branding/color theme — not decided.** Menu currently uses the same parchment/ink/gold gameplay palette as a placeholder (user explicitly said it doesn't have to match). User is weighing personal brand colors (black/blue/silver) vs. aligning with their "NeoGentrics" book-imprint branding vs. something else for Recon Towers Gaming specifically.
- **Play Store dev/publisher account** — which account to publish under (studio name Recon Towers Gaming is resolved; account itself isn't).
- **IAP scope** — cosmetics-only vs. also a patronage/support tier.
- **Scribe "Owned: N" vs. a level-based label** — recommendation given (keep the mechanic, just relabel "Owned: N" → "Level N" cosmetically if wanted), not yet actioned by the user.
- **Scribe output values need rebalancing** once there's real playtesting data — same "placeholder pending playtesting" rule as every other numeric constant, now more urgent given all the stacked multiplier layers (milestone curve, progress multiplier, manager bonus, skill-tree boosts).
- Psalms as a candidate starter/prestige-gate book — user explicitly declined to decide this (2026-07-31: "let's not do that"); don't push it, wait for them to reopen it.

Log the bug (with root cause once found) BEFORE fixing, then update — see the `feedback_live_bug_workflow` memory note.
- **Roadmap process:** `E:\Unity\Clicker Genesis Documentation\Roadmap.html` must always reflect what's actively being worked on, in either parallel session — update it as part of the same pass whenever new work gets planned or scoped, don't wait to be asked.
